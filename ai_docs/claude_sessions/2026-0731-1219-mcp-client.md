# Session: MCP client — servers for the chat agent, and for ced itself

Session ID: 7818d3d8-81c5-4d57-9672-eaa0c876fa9d
Date: 2026-07-31

### Ask

> "I want to be able to connect to an mcp server"

Clarified up front, since the phrasing spans three different jobs:
add an MCP **client to ced** (chosen), configure Claude Code's own MCP,
or expose ced *as* an MCP server.

### The shape of it: one inventory, two consumers

This is the thing to hold onto — everything else follows from it.

1. **The chat agent.** Enabled servers are declared in ACP's
   `session/new` `mcpServers` array; the AGENT spawns its own copies and
   calls the tools during a turn. This is the path that makes MCP useful
   day to day and it needs no connection from ced at all. Agent-agnostic
   — not a Copilot feature.
2. **ced itself.** Connecting from ≡ → MCP is what lets a user verify a
   server works, read its tool list, and run one by hand.

`session/new` was already sending `"mcpServers": []any{}`, so consumer 1
was a hook point waiting for a payload.

### What shipped

New packages / files:

- `internal/lsp/ndjson.go` — `StartNDJSON(dir, bin, args, env, …)`
- `internal/mcp/config.go` — the `mcp.json` inventory
- `internal/mcp/client.go` — the MCP client
- `internal/app/mcp.go` — state, lifecycle, ≡ surfaces, declaration
- plus a `_test.go` for each

**Transport: no new one.** MCP stdio framing IS ndjson, which
`internal/lsp`'s client already speaks (`ndjson: true`, the ACP flag).
So `StartACP`'s body moved into `StartNDJSON` and `StartACP` became a
one-line alias. The one capability added is `env`: MCP servers routinely
need credentials handed to them, and they're APPENDED to `os.Environ()`
— an `npx`-launched server that loses PATH and HOME never starts.

**The config file is `~/.config/ced/mcp.json`, in the ecosystem's
shape** — `{"mcpServers": {name: {command, args, env, …}}}`, VS Code's
`"servers"` accepted as a fallback spelling — so a user pastes the block
they already have instead of hand-translating it. A separate file from
`config.json` for the actions.json reason: flat toggles the ≡ writes back
vs. a nested inventory the user hand-edits, and a syntax error in one must
not disable the other. `userconfig` owns only the path (`MCPPath()`); the
parser lives in `internal/mcp`.

Entries validate at load (`stdio` needs a `command`, `http`/`sse` need a
`url`, unknown `type` is a typo worth reporting) and come back **sorted by
name** — JSON objects have no order, so sorting is what keeps the picker
and the agent declaration stable across runs. `disabled: true` is
honoured and the entry is still RETURNED, so the UI can grey it rather
than pretend it doesn't exist.

**The MCP client (`internal/mcp/client.go`).** Three protocol details
that matter:

- The handshake is three steps, not two: `initialize`, then the
  `notifications/initialized` NOTIFICATION. A server may legally refuse
  everything until that lands.
- Servers make requests of the CLIENT. ced answers `ping` and
  `roots/list` (a `file://` URI for the workspace — that's how a server
  scopes itself to the open project, and answering it is the obligation
  that comes with declaring the `roots` capability) and honestly declines
  `sampling/createMessage` and `elicitation/create`: they want an LLM and
  a prompt surface this package hasn't got.
- `tools/list` paginates. Reading only the first page silently hides
  tools, so the cursor is followed (with a repeat-cursor guard so a buggy
  server can't spin forever).

Timeouts are budgeted per call, not shared: 60s connect (npx/uvx may
DOWNLOAD the server on first run), 15s list, 120s tool call.

**stdio only, deliberately.** `http`/`sse` entries parse and are declared
to the chat agent; ced's own `Connect` refuses them with a message that
points at the alternative rather than just failing. Half-implementing a
second transport would have been the bigger sin.

### App layer

`App.mcp` (`mcpState`) holds the inventory, the load error, and a
`map[name]*mcpConn`. `New` READS `mcp.json` but spawns nothing — "I
declared a server" must never mean "the editor launched three node
processes while I wasn't looking". ced connects only on a deliberate ≡
action; the agent starts its own copies separately.

Surfaces, all through the palette (the house rule — every choose-one UI
is `openPicker`):

- **≡ → MCP → MCP servers…** — rows carry a status glyph, all
  single-width per the chat panel's marker rule: `●` connected +
  tool count, `◌` connecting, `✕` failed + the first line of WHY, `○`
  idle, `·` disabled. Empty inventory or a config error opens the setup
  help instead of a picker with no rows — "where do I declare one?" is
  the question a user with no servers is actually asking.
- **Per-server actions** — Tools… / Connect / Reconnect / Disconnect /
  Server info. Rows that would no-op are OMITTED, not dimmed (the git
  panel's rule); a remote server keeps only Server info, which says why.
- **Tool picker → JSON-arguments prompt**, pre-filled from the tool's own
  schema (`mcpArgSkeleton`: required properties with an empty value of
  their declared type). `"{}"` means "just run it" — a tool needing
  nothing runs on selection rather than making you confirm an empty
  object. Bad JSON flashes the parse error and hands the TEXT BACK, so a
  missing brace costs one keystroke.
- **Result** opens in the info modal, which grows a row per line and does
  NOT scroll — hence a capped preview (22 lines × 78 cols) with a footer
  naming what was cut, and the full text kept on `mcp.lastResult` for the
  **Copy last result** row. A UI that silently truncates reads as one
  that showed you everything.

Contracts inherited from the other integrations, all of them load-bearing:

- **Silent degradation, per server.** One that won't start gets a `✕`
  row with the reason; no modal. The exception is a user standing there
  waiting for a tool list (`toolsWanted`) — they get a flash, because the
  picker they asked for is never going to open.
- **No auto-restart.** A crashed server settles into a failed row.
  Reconnect is the retry gesture, so a server that crashes on start can't
  spin behind the user's back.
- **Generation-checked.** Every conn carries a `seq`, teardown bumps it,
  and a stale ready event **closes the client it carried** — dropping it
  alone would leak the process the disconnect just disowned.
- **Events only.** Connects and tool calls run on goroutines and post
  `mcp*Event`s; only main-loop handlers touch `App.mcp`.

### The chat declaration

`chatInitialize` gained an `mcpServers []mcp.Server` parameter (resolved
on the MAIN LOOP in `chatEnsureStarted` and carried into the goroutine, so
a session declares what was configured when it started; a later reload
applies to the next connection, like the write capability).

`mcpDeclarations(servers, httpOK, sseOK)` renders ACP's shape — env and
headers as `[{name, value}]` objects, sorted — and returns a transcript
note. The capability gate is the interesting part: `http`/`sse` go out
only if the agent advertised
`agentCapabilities.mcpCapabilities.{http,sse}`, because some agents
reject the WHOLE `session/new` over one unreachable entry — that would
trade a missing server for no chat at all. A dropped server is NAMED in
the note; a silently missing tool is the failure a user can't diagnose.
Empty inventory sends `[]`, never `null` (the field is required).

### Verified against real servers

Two throwaway `//go:build manual` harnesses (deleted after the run — a
network-dependent test doesn't belong in the suite, and the harness
breaking on renamed tool names proved the maintenance cost inside one
session).

**`@modelcontextprotocol/server-filesystem` via npx**, through the APP
layer — a real `mcp.json` in a real XDG config dir → inventory
(`MCP servers… (3)`, rows `○ files`, `· parked (disabled)`,
`○ remote`) → `Tools…` → `◌ connecting…` → picker with **14 tools** →
schema-prefilled `{"path": ""}` → `read_text_file` → result modal
carrying the file's contents, and the same text on `lastResult` for the
copy row. `mcpDeclarations` then produced exactly the `session/new`
payload plus the note
`MCP servers: files / MCP skipped: remote (http unsupported by this agent)`.

**`@modelcontextprotocol/server-everything` via npx**, at the client
layer — handshake (`mcp-servers/everything 2.0.0`, protocol
`2025-06-18`), 14 tools with real schemas, `get-sum(2,40)` → "The sum of
2 and 40 is 42.", `echo`, and two things only a real server can prove:

- **`get-roots-list` came back with our workspace root's `file://`
  URI** — ced's `roots/list` handler answering a real server→client
  request, not a fake.
- **`get-env` showed both `CED_TRIAL` (declared) and `PATH`
  (inherited)** — the append-don't-replace env rule that keeps
  npx/uvx-launched servers working.

An unknown tool name returned `isError=true` with the server's own
message rather than a Go error — the distinction the result modal
depends on, confirmed accidentally when the harness used stale names.

**One fix came out of it.** Nearly every tool result ends in `\n`, and
`mcpResultLines` split on it, so every result modal ended with a blank
row (the modal sizes itself to its line count). Trailing newlines are
now trimmed; interior blank lines are content and survive. Pinned in
`TestMCPResultLines`.

### Not done (deliberate)

- **HTTP/SSE in ced's own client.** Declared to the agent, refused by
  ced with a message that says so. The natural next step if remote
  servers get used.
- **No second panel.** Everything reuses the palette and the info modal.
- **No `notifications/tools/list_changed` handling** — ced re-lists on
  demand (the picker is opened per use), so subscribing would add a
  notification nobody acts on.
- **No config toggle.** The inventory file IS the opt-in; `disabled` per
  entry is the off switch.
