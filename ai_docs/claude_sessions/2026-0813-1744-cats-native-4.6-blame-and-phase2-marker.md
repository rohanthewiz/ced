## Phase 2's ⚠ — small, and one real decision

`tabRect` grew a `MarkerX` so the cell the painter marks is the cell the
router answers for — the close `×` rule applied one column left. The
click focuses the tab and re-opens the four-choice prompt.

**Only `⚠` is a button.** `⊘` and `●` have no question behind them (a
deleted file is answered by saving, an unsaved buffer by the save verb),
and a marker that WROTE on click would be the tab strip's one
destructive cell — one column from the filename. They fall through to
the tab switch a click on a tab has always meant.

The raise itself became `raiseConflictNow`, shared with the save guard.
Both are the ON-DEMAND path — the user just performed a gesture about
this file — as against `conflictAfterEvent`, which waits until it is
sure it is not interrupting. It focuses the tab first, because every
resolution acts on the ACTIVE one.

## 4.6 — the blame layer

### (a) The decoration layer could not carry it as it stood

Blame is TEXT the file does not contain. A `Span` restyles characters
the user already has; a `GutterMark` is one cell. So the layer gained a
third primitive — `LineAnnotation` + `AnnotationSource` — and unlike the
other two it **makes room**: the column opens between the line numbers
and the mark cell, and `gutterCols()` replaces the `gutterWidth`
constant everywhere the renderer converts buffer columns to screen
cells.

That is the whole risk of this item. The mitigation is that
`EnsureVisible`, `PosScreenCell` and `HitTest` read a width CACHED at
render time: geometry answers about the frame the user is looking at,
never about the one being computed. A hit-test using a width the screen
doesn't have would put the caret several characters from the click. The
line numbers deliberately do not move — they anchor the left edge, so
switching the column on doesn't slide the one column you navigate by.

The column is all-or-nothing: below `annMinContent` (24 cells of code)
it is dropped whole rather than shrunk, the git-log chips' rule.

### (b) It blames the BUFFER

`git blame --porcelain --contents -`, buffer text on stdin. Blaming the
file on disk would misattribute every line below an unsaved insertion —
annotations that are confidently wrong, which is worse than none. Lines
just typed come back under the all-zero hash and read `— you now` in the
diff gutter's added color.

`--porcelain` and not `--line-porcelain`: a commit's details appear once
and are referred to by hash afterwards, so the parser carries a
hash→details map. The header is recognized by SHAPE (40 hex digits then
numbers) because a commit summary is arbitrary text and must never be
mistaken for a new group.

### (c) Two rules were wrong until the thing was rendered and read

Dumped a real blame of a real ced file to a `SimulationScreen` and
looked at it. Two findings, neither reachable by reasoning:

- **An empty margin.** "Annotate only where authorship changes" meant
  that scrolling into the middle of a file written in one commit gave
  eighteen cells of nothing — on a screen whose answer is "all of this
  is that one commit". The run's stamp is now re-drawn on the first
  VISIBLE row: the top row is a heading, the rows below it are
  boundaries.
- **"External file (--contents)"** — git's label for an uncommitted line
  when asked this way (plain blame says "Not Committed Yet"). The
  mechanism was leaking into the margin. Who an uncommitted line belongs
  to is now decided by the HASH, never by the name git puts on it.

### (d) Staleness is correctness here, not tidiness

With `--contents` every answer describes one exact revision of the
buffer, so a slow early answer landing last would annotate today's lines
with yesterday's authorship. Results are dropped by a per-path sequence
number; the re-ask is a 900ms settle timer keyed to `EditRev` (auto-save's
signature, so no edit path is hooked). The previous column stays up
meanwhile — blanking between keystrokes would be a flicker nobody can
switch off.

Column width is measured over the WHOLE file, once per result: a width
taken from the visible rows would slide the code sideways as it
scrolled.

### (e) The click needed a way to name a commit the panel never loaded

The log holds the newest 400 across `--all`, and the commit that wrote
the line you are pointing at routinely is not among them. So the search
bar gained a fifth mode, `c:<rev>` — "this commit and the history behind
it". It is the one mode that must NOT carry `--all`, which would union
the whole repository back in and bury the commit asked for. Spelled `c:`
and not `#` because `#42` is how people search a message for an issue
number. A commit already in the list is just a selection change, and
leaves a search the user arranged alone.

A click on the column reveals the commit, moves no caret and starts no
drag (the Alt+click rule). Every row of a run answers, including the
ones whose annotation is drawn further up: the column belongs to the
line, only the ink is shared.

### (f) Surfaces, and the row that refuses to switch the layer on

`Esc A` (git's own other name, `annotate` — NOT a shifted twin of `a`,
which is the AI NAMESPACE, a prefix rather than a verb, so the h/H
convention has nothing to say), ≡ Git → "Show/Hide blame", and ≡ Git →
"Blame this line…" as the keyboard twin of the click. That last one
deliberately does not turn the column on: it parks the question and
answers it when git does, because a row about ONE line that switched on
a whole layer would be the menu answering a question of its own.

Session-only, not persisted: it costs a `git blame` per file opened, and
a preference that silently forks on every open is not one to restore
without being asked.
