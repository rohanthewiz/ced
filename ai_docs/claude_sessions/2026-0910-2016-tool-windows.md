## What was asked

Four prompts, each reacting to the last one running:

> Add the concept of tool windows similar to JetBrains products. So the
> git panel becomes a tool, and the filetree also, and grsh terminal, and
> anything I missed. Also I should be able to dock the tool window
> left,right,or bottom. Remember my layout for each project. New projects
> start off with the default layout which is filetree on the left, editor
> occupies the rest.

> Okay having seen the new UI: 1) let's drop the stripes. We will use the
> menu only. Now the bottom tool window should win over the left or right
> tool windows for the bottom area. For example the git panel should
> stretch all across the bottom while the file tree gets the remaining
> space on the left.

> give the file tree a bottom dock header with a close button

> yes, add a ✕ to the vertical docks too

Three design questions were asked up front (stripes yes/no, what replaces
the tree flip, globals vs. per-project); all three took the recommended
option. The stripes were then built, seen, and **removed** by the second
prompt — which is the single most instructive thing in this session and
is recorded as such below.

## The shape of the change

Before this, each auxiliary panel owned its own geometry AND its own
exclusivity rules, and the two were spelled out again in every file: the
terminal knew it had to close the git panel, the git panel knew it had to
close the terminal, the compare panel knew about all four, and
`termDockLeft` flipped the FILE TREE to the other edge. That worked while
there were two panels and one axis. It could not answer "put the git
panel on the right", because nothing in the editor had a notion of a
right edge at all.

Now every auxiliary surface is the same KIND of thing — a **tool window**
that lives on one of three edges, can be moved to another, and is
remembered per project. Seven of them: Explorer (the file tree), Git, Git
log, Problems, Compare, Terminal, Chat.

```
┌────────┬────────────────────────────────────┬────────┐
│        │ tab bar                            │        │
│  left  ├────────────────────────────────────┤ right  │
│  dock  │                                    │  dock  │
│        │ editor                             │        │
│        ├────────────────────────────────────┤        │
│        │ find bar                           │        │
├────────┴────────────────────────────────────┴────────┤
│ bottom dock                                          │
├──────────────────────────────────────────────────────┤
│ status bar                                           │
└──────────────────────────────────────────────────────┘
```

### The five new files

```
toolwindow.go   the registry, the edges, the clamps, every dock rect
tooladapt.go    each panel's show/hide verbs — the seam to the layer
toolheader.go   a dock's header rule, title and ✕, for a panel with none
toollayout.go   the per-project layout: encode, restore, save
toolmenu.go     ≡ Tool windows: tool picker, edge picker, reset
```

### An edge shows one tool at a time

That is JetBrains' rule, and it was also ced's — just written out six
times. `claimDock` states it once, and the panels keep only what is
theirs. The **file tree flip is gone**: chat defaults to the RIGHT edge
now, the tree is a tool docked left, and a claimed edge simply hands the
slot over. `termDockLeft` is retired; `treeOnRight()` survives as a
question about where the user put the Explorer tool, not as a layout
rule.

The ≡ "Dock terminal left" row survives as a named PRESET over
`moveTool`, because it is the move people were already making daily.

### The bottom edge wins the corners (2nd prompt)

The bottom dock spans the WHOLE window and the side docks stop above it,
so a git panel gets the full width for a file list and a diff side by
side while the tree keeps its columns above. The other way round is what
ced did while the only vertical strip WAS the file tree, and it reads
wrong the moment the bottom panel is the one being worked in: the widest
surface in the editor was the one getting narrowed.

Two consequences fell out of it, both recorded in CLAUDE.md:

- **the side seam's hit test had to become ROW-AWARE.** Below the bottom
  dock's top edge, the seam's column is the git panel's own content — a
  column-only test claimed a press inside the panel as a sidebar drag,
  which made its left edge unclickable and started a resize nobody asked
  for.
- **the find bar moved above the bottom dock**, hugging the EDITOR rather
  than the window. It is about the file in front of you, and a bar pinned
  below a git panel is a long way from the line it is searching.

### Sizes

Per tool, per axis — a tree wants 30 columns and a terminal 60, so an
edge-wide width would make every switch a resize, and a terminal dragged
tall at the bottom keeps that height when it comes back from the left.
Zero means auto. **A width is the whole BLOCK, splitter included**, which
is the convention every width in this editor already used; aligning on it
is what let stored numbers keep meaning the same thing across the
rewrite.

The Explorer's width is the ONE special case: it stays on
`App.sidebarWidth`, because auto-fit re-derives that field every frame, so
it is the LIVE number and a copy in the layout's size map would be a
second one that could disagree with the screen. `storedToolWidth` reads
through to it.

### Per-project persistence

`session.Entry.Layout`, beside that folder's tabs — a layout answers
"what am I doing in this repository", and it is machine churn, which is
the split state.json exists to make. Nothing about tool windows lives in
config.json. A project with no record gets the default: Explorer left,
editor taking the rest. The stored dock map is SPARSE, so an unarranged
project writes almost nothing and a default changed later reaches users
who never touched that tool.

### The header (3rd and 4th prompts)

Six of the seven tools were BORN as bottom strips and arrived with a rule,
a title and a ✕. The file tree was a sidebar for the editor's whole life,
so it had a ✕ on no dock at all, and once it could sit at the bottom it
had no resize handle either.

`toolDef.ownHeader` says who brings their own; anything that does not gets
the generic one, on EVERY edge:

```
─ Explorer · 22 marked ── ✕ ─│  ≡
 ced                         │
✓▸ .cats-todo/               │
```

It **costs no rows**: the tree gives up its own EXPLORER row for it
(`filetree.Tree.HideLabel`), so the header replaces a row rather than
adding one, and the mark count moves into it — that row was the mark
set's only always-visible surface.

What the rule DOES depends on the edge: the height-drag handle at the
bottom (no seam down there), inert on a vertical edge (the seam already
resizes it) but still swallowed, exactly as the unclickable EXPLORER row
it replaced was.

## The stripes, built and then removed

The first prompt asked whether to draw JetBrains' tool-button rails; the
answer was yes, they were built (`toolstripe.go`, 263 lines + 229 of
tests), and the second prompt deleted them after seeing them run. Worth
recording, because the reasoning is now in CLAUDE.md as a rule rather
than as a scar:

> the editor is the whole window minus what you asked for, and a
> reserved column on three edges is a price you go on paying for every
> tool you are NOT currently looking at.

The argument FOR them was real — single occupancy means most tools are
collapsed most of the time, and this editor's own lore says "a row nobody
can find is worse than a row that explains itself". It lost to the cost.
Reach is now the ≡ menu: the three-row Tool windows group plus the
per-panel Show/Hide rows each panel already had. `"toolstripes"` went with
them and is ignored if left in a config.json.

## Bugs found on the way

Four, all real, all pinned by tests:

1. **The layout is restored during `New`, BEFORE the window has a size.**
   Clamping there floored every remembered extent to its minimum, so the
   editor appeared to forget the layout it had just promised to remember.
   `clampToolSizes` now refuses an unsized window; reads clamp anyway,
   which is what makes skipping the write-back safe.
   (`TestApplyToolLayout_SurvivesAnUnsizedWindow`)
2. **The empty-editor placeholder was centred but never clipped.** With a
   vertical dock taking columns it painted over the seam and into the
   panel beside it. `drawCentered` now clips to the band.
3. **The side seam's hit test was column-only** — see "the bottom edge
   wins the corners" above. (`TestDockSplitterHit_EndsAtTheBottomDock`)
4. **The consolidated dock-drag branch passed the pointer's X for all
   three edges.** Silently harmless while only vertical seams used it;
   the bottom edge needs the ROW, and the generic header is the first
   thing to drag through that mode.

A fifth near-miss: the git panel's first `minW` on a vertical edge was
`list + diff + 3` = 67 columns, which made it undockable beside anything
else on a laptop. Lowered to the LIST pane's floor plus the seam, per the
Find-all dock's precedence rule — `gitPanelListWidth` already compresses
the diff pane rather than refusing.

## Shipping it (a second wrap, same session)

Two prompts after the first `/sess-wrap`, both small, both recorded here
rather than in a doc of their own — same session, same subject, and
"where did this ship?" is a question you ask of the feature's doc.

### The README pass (`37daf59`)

> So how do I move a tool window to another location?

The answer was worth writing down, so a **`### Tool windows`** section
went into Usage: the three edges, the two-pick move (`Esc k` → "move
tool", or ≡ → View), a table of the four rows, the three rules that
surprise people, resizing, and where the layout is stored. The layout
sketch is a **real capture** rather than a drawing, so it cannot drift
from what ced paints.

Going through the README turned up four things tool windows had made
**wrong**, not merely incomplete — worth noting as a pattern, since none
of them would have failed a test:

- the chat section still said the panel docks **left** and "the file tree
  slides over to the right while it's open". Both halves false now.
- "the chat panel and a **left-docked terminal** share the left edge" was
  a rule about two named panels; it is a rule about any edge.
- the sidebar was "toggleable, draggable" — it is movable and closable
  too.
- `Esc =` / `Esc -` were never in the hotkey table at all, and they are
  the keyboard path to resizing whatever you are working in.

### The release (`d30ed59`, tag `v0.3.0`)

> Please bump CEd's git tag and reflect the same in the toml

**There is no `.toml` in this repo**, and that is worth recording so the
next person does not go looking. The version lives in exactly two places:

- `internal/version/version.go` — `const Version`, the source of truth.
- `Formula/ced.rb` — written BY GoReleaser, carrying real sha256 sums of
  the published tarballs. Hand-editing it points Homebrew at URLs that do
  not exist yet with checksums that do not match.

Two near-misses for "the toml": `.goreleaser.yml` has `version: 2`, but
that is the GoReleaser CONFIG SCHEMA version, not ced's — there is no app
version in that file at all.

Bumped 0.2.0 → **0.3.0** (163 commits, a new subsystem, a retired config
key, a changed default dock), and tagged **by hand** rather than through
`release.yml` at the owner's call. So the tag is a marker only: no
binaries, no GitHub Release, and `Formula/ced.rb` still says 0.2.0, so
`brew install ced` still gets the old build.

Mixing the two paths later is safe by construction — the workflow's tag
step does `git rev-parse --verify refs/tags/v$NEW` and skips its own
tagging when the tag already exists, then runs GoReleaser against it and
rewrites the formula. That check is the one place the manual and
automated paths were designed to meet.

## For next time

- **A bottom-docked Explorer is usable but cramped** on purpose: the git
  panel's list/diff seam and the log's list/detail seam were designed for
  a wide strip and will clamp hard on a narrow vertical dock. They work;
  they are not pretty. Nobody has asked for them there yet.
- **The Find-all list is deliberately NOT a tool window** — its own file
  explains why it is not even a picker (a live preview, an Esc that puts
  the view back), and it docks TOP, an axis no tool window has. Folding
  it in would mean giving every tool window a preview hook and a cancel
  that undoes.
- **Chat's default edge moved to the right.** Anyone with muscle memory
  for it on the left can move it back in two picks, and that choice now
  persists per project.
- `toolLayoutSummary()` exists and has no reader outside tests. It was
  written as a debugging aid; if a status-bar or ≡ label ever wants to
  say where everything is, it is already there and already stable.
- **v0.3.0 has no artifacts.** To publish them, dispatch the release
  workflow on this version — it will skip tagging (the tag exists),
  build, and rewrite `Formula/ced.rb`. This repo is a FORK, so a push to
  `release` triggers nothing: it needs
  `gh workflow run release.yml --repo rohanthewiz/ced --ref release`.
- **The README is now a place tool-window changes can go stale.** Four
  of its claims were wrong after this session and no test caught any of
  them. If the docking defaults move again, `### Tool windows`, the
  Features list, the chat section and the hotkey table are the four
  spots.
